02 · Scope and limitations

The assessment is limited to the configured model API. Application integration, tool execution and downstream impact are explicitly out of scope unless recorded as observed evidence.

In scope

  • The configured model API endpoint and model identifier at the time of the assessment.
  • The system prompt, harness instructions, temperature, token limit and request budget recorded on the assessment.
  • Prompt-level behaviour: instruction following, policy adherence, protected-context disclosure, tool-call emission and output content.

Out of scope

  • The surrounding application UI, HTML/Markdown renderer, browser, mobile client or downstream data sinks.
  • Tool authorization, tool execution, privilege boundaries and downstream side effects.
  • Retrieval stores, document ACLs, cross-tenant isolation and vector-database configuration.
  • Infrastructure, network services, identity providers, payment systems and production data.
  • Sustained load, availability under concurrency, recovery behaviour and cost impact.

04 · Methodology

Bounded testing with evidence-aware conclusions

ZeroDay's LLM Rakshak executes a bounded library of canary-based security tests against the configured model API. Each module defines an explicit procedure, secure and vulnerable behaviours, detector rules and a remediation. The harness sends the procedure with synthetic per-run canary values, captures the raw model response, and evaluates it with deterministic detectors (unique canaries, protected values, policy markers, tool-call inspection and structured response checks) supplemented by pattern and refusal analysis. Findings are then classified by what the evidence actually supports: model behaviour is not treated as application impact, and a tool call emitted by a model is not treated as an executed tool call.

PhaseWhat happens
AuthorizationThe assessment records the customer's ownership confirmation, authorization statement and explicit endpoint-owner confirmation before execution.
Test selectionBuilt-in modules are selected by preset or explicit test IDs and filtered by the organization's plan and the target's supported modalities.
Bounded executionEach module runs within the assessment's request/token budget and intensity profile. The harness never executes model-suggested tools or renders model output.
Evidence captureRequests, responses, tool calls, status, latency, detection rules and per-run canary context are captured with redaction applied at capture time.
ClassificationEvidence is classified as confirmed, likely, unsafe behaviour, potential, inconclusive or false positive. Application impact is separated from model behaviour.
ScoringScoring 2.0: severity-weighted tested results with classification factors; only confirmed/likely findings cap the score; untested tests never count as secure.
ReportingThe same normalised model renders HTML, PDF, JSON and CSV with identical counts, classifications, timestamps and evidence hashes.
